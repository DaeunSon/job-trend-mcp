# job-trend-mcp 고도화 설계 — "운영되는 채용 데이터 서비스 + AI 커리어 기능"

작성일: 2026-11-21 · 상태: 사용자 검토 대기 (남은 질문 4개 답 반영, §12)

> 표기: **[결정]** 은 사용자가 대화에서 정한 것, **[제안]** 은 설계자가 정한 기본값(사용자가 바꿀 수 있음), **[빌더]** 는 구현자가 정해도 되는 것.

---

## 1. 의도와 이유

- **누가 · 왜:** 백엔드 · 인프라 직무를 준비하는 취업준비생(이 저장소의 주인)이 포트폴리오로 쓴다. **[결정]**
- **무엇을 증명하고 싶은가:** "내가 설계하고, 배포하고, 운영하고, 개선한 서비스"를 **측정한 숫자**로 말할 수 있어야 한다.
  면접에서 "왜 이 도구를 썼나", "장애 · 비용 · 실패를 어떻게 다뤘나"에 실제 경험으로 답할 수 있는 것이 목표다.
- **왜 새 프로젝트가 아니라 고도화인가:** 수집 · 정규화 · MCP · 평가가 이미 탄탄하고(테스트 1,108개, MCP 전후 비교 실험 0/18 → 18/18),
  비어 있는 것이 정확히 백엔드 · 인프라 영역(DB, API, 배포, 모니터링, 보안)이라서. **[결정]**
- **AI가 반드시 들어가야 한다.** 단, "LLM을 호출했다"가 아니라 비용 · 지연 · 실패 · 정확도를 다룬 운영 가능한 형태로. **[결정]**
- **참고 서비스:** 하퍼(matchharper.com, AI 커리어 에이전트)의 구직자 기능 중 일부를 **이 프로젝트가 모은 시장 데이터를 근거로** 구현한다. **[결정]**
  차별점은 "국내외 11개 사이트 실제 공고 통계가 근거"라는 것.
- **누가 쓰는가:** 처음에는 **본인과 지인 소수(초대한 사람만)** 로 시작하고, 운영이 안정되면 **일반 공개**로 넓힌다. **[결정]** 넓히는 조건은 §12.1.

## 3. 목표 · 비목표 · 반목표

**목표**
1. 공개 도메인(HTTPS)에서 상시 운영되는 서비스. 매일 수집된 데이터가 자동으로 DB에 쌓이고, 시계열 트렌드를 제공한다.
2. 인프라를 **수동 → 컨테이너 → 코드(IaC) · 자동화 → 운영 → 확장** 순서로 직접 밟아, 각 도구가 왜 필요한지 경험으로 설명할 수 있다. **[결정]**
3. AI 기능 3종: LLM 데이터 보강, 의미 기반 매칭, 커리어 상담 · 이력서 제안. 각각 정확도 · 비용 · 지연을 측정한다. **[결정]**
4. 구직자 기능: 맞춤 공고 추천, 새 공고 알림, 회사 채용 동향, 이력서 맞춤 제안, (덤) 면접 예상 질문 · 지원 현황 관리. **[결정]**
5. 단계마다 면접에서 쓸 **전후 수치**가 기록으로 남는다(§9).

**비목표**
- 자동 지원, 채용 담당자 · 창업자 연락처 수집 및 이메일 발송 (약관 · 개인정보보호법 · 스팸 문제). **[결정]**
- 기업용 기능(후보자 추천, 소개 요청, 결제) — 양면 마켓은 1인 범위 밖. **[결정]**
- 상용 서비스화 · 유료 결제. 포트폴리오용 비영리 운영으로 둔다. **[제안]**
- 고가용성 다중 서버 · 멀티 리전.

**반목표 (기술적으로 돌아가도 실패로 보는 것)**
- 관리형 서비스로 처음부터 감싸서, 그 아래에서 일어나는 일을 설명하지 못하는 상태.
- 클라우드 · LLM 비용이 통제되지 않음 (예산 알림 · 하루 상한 없이 운영).
- HTML 크롤링 사이트의 원문 공고를 공개 서비스에서 그대로 재배포해 약관 문제를 만드는 것.
- AI 기능을 붙였지만 정확도 · 비용을 측정하지 않아 "좋아졌다"를 숫자로 말 못 하는 것.
- 기존 MCP tool 5개, 테스트 1,108개, `evals/` 가 깨지는 것.

## 4. 제약

- **1인 개발. 1차 구현 마감은 2026-11-28(토).** **[결정]** 1주 안에 할 범위와 그 뒤로 미루는 것은 §12.2.
- **예산:** 클라우드 월 2~3만 원(작은 EC2 1대). **[결정]** AWS 예산 알림 필수. LLM API는 클라우드 예산과 따로 잡고 하루 비용 상한을 코드로 강제(§12.4).
- **수집 위치:** 일부 국내 사이트가 클라우드 IP를 막을 수 있어, 수집은 당분간 **GitHub Actions에 그대로 두고 결과만 서버로 보낸다.** **[제안]**
- **LLM 제공자:** 저장소가 이미 Anthropic SDK(`anthropic>=1.13`)를 쓰므로 Claude를 기본으로 한다. 대량 추출은 소형 모델(Haiku급), 상담은 중형 모델(Sonnet급). **[제안]**
- **임베딩:** Anthropic에는 임베딩 모델이 없다. 한국어 · 영어를 모두 다루는 다국어 임베딩이어야 한다. API형(예: Voyage)인지 자체 호스팅 소형 모델인지는 비용 · 서버 메모리(작은 EC2)를 보고 **[빌더]**.
- **개인정보:** 이력서 · 프로필은 민감 정보다. 최소 수집, 사용자가 언제든 삭제 가능, LLM 호출 시 필요한 부분만 전송, 로그에 원문을 남기지 않는다.
- **약관:** 공개 화면에서는 공고 원문 전체를 재배포하지 않고 요약 필드 + 원문 링크만 보여준다. **[제안]**

## 6. 단계별 설계

각 단계는 독립적으로 배포 · 시연 가능해야 하고, 끝날 때 §9의 수치를 기록한다.

### 1단계 — 운영 기반 (인프라 경로 1~4)

**1-1. 손으로 직접 [결정]**
- AWS 콘솔로 VPC/서브넷/보안그룹, EC2(ARM 소형) 생성. SSH로 접속해 Python 앱, PostgreSQL, Nginx를 직접 설치.
- 도메인 연결, Let's Encrypt로 HTTPS, systemd로 서비스 상시 실행.
- 이 단계의 불편(재구축 시 반복 작업 등)을 기록해 둔다 → 1-3의 동기가 된다.

**1-2. 컨테이너화**
- API, worker, PostgreSQL(pgvector), Nginx(또는 Caddy)를 Docker Compose로. 볼륨 · 네트워크 · 헬스체크.

**1-3. 코드와 자동화**
- 1-1에서 손으로 만든 것을 Terraform으로 재현(VPC, SG, EC2, EIP, IAM, Route53 또는 외부 DNS). 상태 파일은 S3 원격 백엔드 **[제안]**.
- GitHub Actions: 기존 CI 유지 + 이미지 빌드 → 레지스트리(ECR 또는 GHCR **[빌더]**) → 서버 배포.
- 민감정보는 저장소에 두지 않는다(GitHub Secrets, AWS SSM Parameter Store **[제안]**).

**1-4. 백엔드 기반 (1-1~1-3과 병행)**
- **DB 도입:** JSON → PostgreSQL. **[제안]** 지금 tool들은 `store.postings` 등 메모리 리스트를 파이썬으로 거르는 구조라, 인터페이스를 그대로 두면 DB 전체를 메모리에 올리게 되고 새 필터 · 시계열 · pgvector가 store를 우회하게 된다. 그래서 **조회는 SQL로 옮기고, 지켜야 할 것은 tool의 입력 · 출력 계약**(`test_mcp_tool_contract` 등)으로 한다. JSON fixture로 store를 만드는 테스트는 DB fixture로 바꾼다.
- **수집 → DB 연결:** `collect.yml` 마지막에 정규화된 공고를 서버의 **인증된 수집 전용 엔드포인트**로 업로드 **[제안]** (DB 포트를 외부에 열지 않기 위해). 같은 공고 재업로드는 멱등 처리.
- **시계열:** 공고마다 `first_collected_at` / `last_seen_at`(기존 `schemas.py` 필드 이름 유지), 수집일별 관측 기록. 일 · 주 단위 스킬 · 직무 집계 테이블(또는 materialized view).
- **수집 표본과 트렌드의 해석 [제안]:** `collect_plan.json`은 사이트마다 수집 상한(`--max-jobs 60`, `--max-pages 2` 등)이 있어 하루 수집은 전수가 아니라 **표본**이다.
  - 트렌드는 "건수"보다 **비율**(예: 백엔드 공고 중 Kubernetes 요구 비율)을 주 지표로 하고, 화면에 "수집 표본 기준"임을 표시한다. 수집 계획(상한 · 검색어)은 버전으로 기록해, 계획이 바뀐 날은 차트에 표시한다.
  - 상한은 공식 · 내부 JSON API 사이트(원티드, 점핏, 랠릿, Remotive 등)부터 실행 시간 · 요청 빈도 한도 안에서 올린다. HTML 크롤 사이트는 약관 · 차단 위험 때문에 현행 유지.
  - **마감 판정은 "미관측"으로 하지 않는다**(상한 밖으로 밀려난 것과 구분 불가). 마감일 필드가 있으면 그것으로, 없으면 worker가 상세 페이지/API를 낮은 빈도로 재확인해 판정한다.
  - "새 공고 알림"의 "새로움"은 사이트의 게시일(있으면) 기준, 없으면 `first_collected_at` 기준으로 하고 그 한계를 문서화한다.
- **REST API:** FastAPI **[제안]**. 공고 검색(기존 필터 + 경력 · 스킬 · 급여 범위 · 게시일 · 키워드), 스킬 트렌드(기간 비교), 직군 · 급여 · 회사 통계. 페이지네이션.
- **MCP 서버:** 같은 DB를 보도록 전환, 공개 엔드포인트로 상시 운영(ngrok 제거). 기존 5개 tool 유지 + 트렌드 tool은 시계열을 반환하도록 확장.
- **인증 · 제한 [제안]:**
  - REST API(웹 화면용): 사용자 세션 인증 + 요청 수 제한. 사용자 계정 방식은 3단계에서 **[빌더]**.
  - 공개 MCP 엔드포인트: Claude 웹 커스텀 커넥터는 정적 API 키 헤더를 보낼 수 없고 OAuth를 쓴다. 그래서 1차로는 **인증 없는 읽기 전용(공개 시장 데이터 tool만) + IP별 요청 제한**으로 운영한다. 개인 기능(매칭 · 이력서 · 알림)은 MCP로 노출하지 않고 웹에서만 제공한다. MCP용 OAuth 2.1은 선택 과제(5단계 이후)로 둔다.
  - 수집 업로드 엔드포인트: 별도 비밀 토큰(GitHub Secrets).
- 문서에 있던 개선 과제(`pyproject.toml` + editable install로 `PYTHONPATH` 제거)도 이때 처리.

**1-5. 운영**
- 지표 · 대시보드: Prometheus + Grafana **[제안]** (API 지연 · 오류율, DB, 수집 성공률, LLM 비용). 외부 가동 감시 1개.
- 알림: 장애 · 수집 실패 · 비용 임계치 → 텔레그램 또는 이메일 **[빌더]**.
- 백업: PostgreSQL 일일 백업 → S3, **복구 리허설 1회 이상 기록**.
- **보안 점검:** OWASP ZAP으로 공개 API 스캔 → 발견 · 조치 · 재스캔 기록.
- **부하 테스트:** k6 시나리오(검색 · 트렌드 · 매칭) → 병목 분석 · 개선 전후 기록.
- **AI 운영 보조(④):** 수집 실패 로그, ZAP · k6 결과를 LLM이 요약해 알림으로 보낸다(원인 추정 + 조치 제안).

### 2단계 — LLM 데이터 보강 (①)
- 대상: 숫자 급여, 고용형태, 경력, 직무, 스킬이 비어 있거나 미분류인 공고.
- 구조: 수집 후 보강 작업을 큐에 넣고 worker가 일괄 처리. 공고 본문 해시로 캐시(같은 본문은 재호출 안 함), 재시도 · 백오프, **하루 비용 상한 도달 시 중단**.
- 출력은 기존 taxonomy 값으로 제한(구조화 출력). 규칙 기반 값이 있으면 규칙 우선, LLM 값은 출처(`source=llm`, 모델, 시각)를 함께 저장해 되돌릴 수 있게.
- 측정: 사람이 정답을 단 표본 세트로 필드별 정확도, 결측률 전후, 1천 건당 비용, 처리 시간. 기존 `evals/` 구조를 재사용 **[제안]**.

### 3단계 — 매칭 + 새 공고 알림 (② + 하퍼 핵심)
- 사용자 계정 · 프로필(스킬, 경력, 희망 직무 · 지역, 선택적으로 이력서 텍스트). 처음에는 **초대받은 사람만 가입**(허용 목록 또는 초대 코드), 일반 공개 때 공개 가입으로 바꾼다(§12.1).
- 공고 임베딩 저장(pgvector) + 키워드 · 필터와 섞은 하이브리드 검색. 기능: 프로필 → 맞춤 공고, 비슷한 공고, **사이트 간 중복 공고 탐지**.
- 저장한 조건 · 프로필에 맞는 **새 공고가 수집되면 알림**(이메일 또는 텔레그램). 같은 알림이 두 번 가지 않게 멱등 설계, 실패 재시도.
- 회사 채용 동향: 기존 회사 tool을 시계열로 확장(채용 속도, 주력 직무, 요구 스킬 변화).
- 측정: 검색 지연(k6), 추천 품질(소규모 수동 평가 세트), 알림 지연 · 중복률.

### 4단계 — 커리어 상담 + 이력서 제안 (③ + 하퍼)
- 자연어 질문 API: LLM이 기존 tool(검색 · 트렌드 · 급여 · 회사 · 매칭)을 골라 호출하고 **데이터를 근거로** 답한다. 스트리밍 응답, 토큰 기준 요청 제한, 시간 초과 · 대체 모델.
- 이력서 맞춤 제안: 공고 vs 이력서 → 강조할 경험, 부족한 스킬(시장 수요 비율과 함께), 수정 제안. **자동으로 고쳐 쓰지 않고 제안만.**
- 덤: 면접 예상 질문, 지원 현황 관리(지원 → 서류 → 면접).
- 원칙(하퍼에서 차용): AI가 사용자 대신 외부로 무언가를 보내는 기능은 만들지 않는다.
- 측정: 기존 `evals/` 방식으로 tool 선택 · 답 정확도, 응답 지연, 대화당 비용.

### 5단계 — 확장 · 비교 (인프라 경로 5)
- k3s로 이전(같은 EC2를 키우거나 Oracle 무료 서버 **[빌더]**), 매니페스트 · 롤링 배포 · 헬스체크.
- DB를 RDS로 옮긴 구성과 비용 · 운영 부담 · 성능을 비교해 기록.
