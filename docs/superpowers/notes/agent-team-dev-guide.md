## 2. "Agent 팀"의 실체

계속 살아 있는 팀원이 있는 게 아니다. **메인 세션(지휘자) 하나가 태스크마다 새 에이전트를 띄우는 구조**다.

| 역할 | 누가 | 하는 일 |
|---|---|---|
| 지휘자 (controller) | 메인 Claude 세션 | 태스크 설명(brief) 작성, 에이전트 실행, 기록 파일 관리, 판단이 필요한 일 결정. **직접 코드를 고치지 않는다** |
| 구현자 (implementer) | 태스크마다 새 에이전트 | 테스트 먼저(TDD) → 구현 → 커밋 → 스스로 점검 → 보고서 작성 |
| 태스크 리뷰어 | 태스크마다 새 에이전트 | diff만 읽고 **명세 일치(✅/❌)** 와 **코드 품질**을 판정 |
| 재리뷰어 | 수정할 때마다 | 지적된 항목이 고쳐졌는지만 확인 (ADDRESSED / NOT ADDRESSED) |
| 최종 리뷰어 | 마지막에 한 번 | 가장 성능 좋은 모델로 브랜치 전체를 리뷰 |

### 핵심 규칙
- **컨텍스트 격리:** 새 에이전트는 대화 기록을 물려받지 않는다. 태스크 설명 파일만 받는다.
- **보고서를 믿지 않는다:** 리뷰어는 구현자 보고서를 "검증 안 된 주장"으로 보고 diff와 대조한다.
- **구현자는 하위 에이전트를 띄우지 않는다:** 리뷰는 지휘자만 맡긴다.
- **구현자는 동시에 여러 명 띄우지 않는다:** 충돌을 막기 위해서다.
- **태스크 사이에 멈추지 않는다.** 멈추는 경우는 네 가지뿐이다.
  1. 되돌릴 수 없는 작업
  2. 보안에 민감한 작업
  3. 외부로 나가는 작업 (merge, 공유 브랜치 push, 배포)
  4. 계획이 완전히 망가져 무엇을 해도 추측인 경우
- **판정 기록(Ruling):** 애매한 건 멈추지 않고 결정하되, 기록 파일에 `Ruling: 결정 — 이유 — 틀렸을 때 비용` 형식으로 남긴다.

## 3. 태스크 하나가 처리되는 과정

1. 지휘자가 시작 커밋(BASE)을 기록하고, 태스크 설명 파일(`task-N-brief.md`)을 만든다.
2. 구현자 실행 → 질문이 있으면 답한다.
3. 구현자가 TDD로 구현하고 커밋한 뒤 `task-N-report.md`를 쓴다. 상태는 아래 넷 중 하나다.
   - `DONE`: 완료
   - `DONE_WITH_CONCERNS`: 완료했지만 걱정되는 점이 있음
   - `NEEDS_CONTEXT`: 정보가 더 필요함
   - `BLOCKED`: 진행할 수 없음
4. 지휘자가 리뷰용 diff(`review-<base>..<head>.diff`)를 만들고 태스크 리뷰어를 실행한다.
5. 명세 ✅이고 품질 승인이면 완료. 아니면 **수정 반복(fix loop)** 에 들어간다.
6. 기록 파일에 `Task N: complete (commits a..b, review clean)` 한 줄을 남긴다.

### 수정 반복 (최대 5라운드)

| 라운드 | 누가 고치나 |
|---|---|
| 1~3 | 원래 구현자가 이어서 수정 (맥락 유지) |
| 4~5 | **더 좋은 모델**의 새 구현자 (새로운 눈으로) |
| 5라운드 후에도 남으면 | 지휘자가 판정: 보류(parked)하거나, 이후 작업에 필요한 최소 수정을 결정(Ruling) |

- 매 라운드는 "수정 1번 + 범위를 좁힌 재리뷰 1번"이다.
- 사소한(Minor) 지적은 수정 반복에 넣지 않고 `minor (deferred)`로 기록해 최종 리뷰로 넘긴다.

### 최종 리뷰
- 브랜치 전체 diff를 가장 성능 좋은 모델로 리뷰한다.
- 지적이 나오면 **수정 에이전트 1명**이 한꺼번에 고치고, 재리뷰는 1번만 한다. 두 번째 수정 묶음은 없다.
- 마지막 메시지에 **"Rulings I made"** 목록이 반드시 나온다.
- 리뷰가 깨끗하면 작업 폴더를 **삭제**한다. ⚠️ 보관하려면 미리 말해야 한다.

### 모델 선택 원칙
- 계획에 코드가 거의 다 적힌 기계적인 작업 → 가장 싼 모델
- 여러 파일에 걸친 통합 작업 → 중간 모델
- 설계 판단이나 최종 리뷰 → 가장 좋은 모델
- **주고받는 횟수가 토큰 단가보다 중요하다.** 싼 모델은 여러 단계 작업에서 2~3배 더 많이 주고받아 오히려 비쌀 수 있다.

위치: `.superpowers/sdd/<계획 이름>/` (git에 올라가지 않음)

| 파일 | 내용 | 검증할 때 볼 것 |
|---|---|---|

| `task-N-brief.md` | 구현자가 받은 요구사항 원문 | 계획 내용이 빠짐없이 옮겨졌는지 |
| `task-N-report.md` | 구현자 보고서 (수정 보고서는 뒤에 추가됨) | TDD 증거: **RED**(구현 전 실패 출력)와 **GREEN**(구현 후 통과 출력)이 실제로 있는지 |
| `review-<base>..<head>.diff` | 리뷰어가 본 diff 그대로 | 리뷰 판정과 내 판단이 같은지 |

## 5. 내가 검증하는 절차 (체크리스트)

### A. 실행 전 — 가장 효과가 큰 단계
- [ ] 설계 문서 승인: 단계마다 "끝났다는 기준"이 측정 가능한 문장인지
- [ ] 구현 계획의 **Global Constraints**에 설계 문서의 값이 그대로 들어갔는지 (예: 기존 테스트 1,108개 유지, 비용 상한)
- [ ] 구현 계획의 **Review Focus** 5줄이 내가 걱정하는 입력·실패 상황을 다루는지
- [ ] 각 태스크의 **테스트 이름과 검증 내용**이 합격 기준으로 충분한지
- [ ] 멈출 지점 지정 (예: "Task 2 끝나면 멈춰") — 내 지시가 스킬 규칙보다 우선한다
- [ ] 작업 폴더 보관 여부 지정 ("작업 폴더는 지우지 말고 보관해")
- [ ] 필요한 스킬이 모두 설치됐는지 확인 (7절)

### B. 실행 중 — 태스크 단위
- [ ] `progress.md`에서 새로 생긴 `Ruling:`을 읽고 동의하는지 판단
- [ ] `task-N-report.md`에 RED/GREEN 출력이 실제로 있는지
- [ ] 커밋을 직접 확인
  ```bash
  git log --oneline main..HEAD     # 태스크별 커밋
  git show <sha>                    # brief와 diff 나란히 비교
  pytest tests/<해당 테스트>.py -q  # 보고서의 테스트 결과를 직접 재현
  ```
- [ ] **테스트가 진짜인지 확인:** 구현 코드 한 줄을 일부러 망가뜨리고 테스트가 실패하는지 본다 (확인 후 되돌리기)
- [ ] **무작위로 골라 직접 리뷰:** 태스크 1~2개를 골라 brief와 diff를 직접 대조하고, 리뷰어 판정과 비교한다

### C. 끝난 뒤
- [ ] "Rulings I made" 목록을 하나씩 읽고, "틀렸을 때 비용"이 큰 것부터 확인
- [ ] `minor (deferred)`와 `parked` 항목 중 merge 전에 고칠 것 고르기
- [ ] 전체 테스트를 직접 실행: `pytest -q`
- [ ] 설계 문서의 "끝났다는 기준"을 실제 서비스에서 확인 (예: HTTPS 도메인에서 API 응답)
- [ ] merge·push는 내가 결정한다 (AI는 요청 전엔 하지 않는다)

### 검증 원칙 한 줄
> **보고서가 아니라 증거를 본다** — 커밋, diff, 내가 직접 돌린 테스트 출력.

## 6. 공부 순서

### 1단계: 파일 읽기 (전체 약 1,350줄)
1. `~/.claude/skills/subagent-driven-development/SKILL.md` (339줄): 전체 흐름, 모델 선택
2. `implementer-prompt.md` (154줄): 구현자가 실제로 받는 지시
3. `task-reviewer-prompt.md` (209줄): 리뷰 기준, 심각도 구분
4. `re-review-prompt.md` (116줄): 범위를 좁힌 재리뷰
5. `references/fix-loop.md`, `final-review.md`, `preflight.md`: 수정 반복, 마무리, 실행 전 충돌 점검
6. `~/.claude/skills/writing-plans/SKILL.md`: 좋은 계획의 조건 — 검증 품질은 결국 계획 품질에 달려 있다
7. 원본 저장소: https://github.com/obra/superpowers

### 2단계: 이해할 개념
| 개념 | 왜 중요한가 |
|---|---|
| 컨텍스트 격리 | 이전 대화가 섞이지 않아 태스크에 집중하고, 지휘자의 컨텍스트도 아낀다 |
| 두 번 확인하는 구조 | 스스로 점검과 독립 리뷰는 서로를 대신할 수 없다 |
| TDD 증거 (RED → GREEN) | 실패를 먼저 보여 줘야 테스트가 진짜 무언가를 검증한다는 게 증명된다 |
| 기록 파일 (ledger) | 대화가 요약되면 기억이 사라진다. 완료된 태스크를 다시 돌리는 게 가장 비싼 실패다 |
| 수정 횟수 상한 + 판정 | 끝없이 돌지 않게 하고, 결정은 숨기지 않고 기록으로 남긴다 |
| 모델 계층 | 역할별로 필요한 만큼의 모델만 써서 비용과 속도를 맞춘다 |

### 3단계: 작게 실습하기
- 태스크 2개짜리 연습 계획으로 한 바퀴 돌려 본다.
  - 예: `.gitignore`에 `data/data-archive/` 추가, `pyproject.toml` 도입
- 기록 파일 → brief → 보고서 → 리뷰 diff가 생기는 과정을 직접 보고, 5절 체크리스트로 검증한다.
- 실습이 끝나면 본 구현(11/22~28 계획)은 **첫날 태스크만 실행 → 검토 → 나머지 실행** 순서로 진행한다.

## 7. 현재 설치 상태의 빈틈 ⚠️

SDD가 불러 쓰는 아래 스킬들이 **설치되어 있지 않다** (2026-11-21 확인).

| 없는 스킬 | 어디서 쓰나 | 영향 |
|---|---|---|
| `using-git-worktrees` | 시작할 때 작업 공간을 따로 만드는 단계 | 브랜치나 worktree를 직접 만들어야 함 |
| `requesting-code-review` (`code-reviewer.md`) | 최종 리뷰 프롬프트 | 최종 리뷰 기준을 임의로 대신 써야 함 |
| `finishing-a-development-branch` | merge/PR 선택지를 보여주는 마무리 단계 | 마무리 절차가 빠짐 |
| `executing-plans` | SDD 대신 쓰는 "직접 실행" 방식 | 대안을 고를 수 없음 |

**할 일:** 구현을 시작하기 전에 superpowers 같은 커밋 기준으로 위 스킬을 설치한다.

## 8. 용어 정리

| 용어 | 뜻 |
|---|---|
| 지휘자 (controller) | 메인 세션. 에이전트를 띄우고 조율한다 |
| brief | 태스크 하나의 요구사항을 계획에서 뽑아낸 파일 |
| ledger | `progress.md`. 진행·판정 기록 |
| Ruling | 지휘자가 사람 대신 내린 결정과 그 이유·비용 |
| parked | 수정 상한에 도달해 보류한 지적 |
| BASE / HEAD | 리뷰 범위의 시작 / 끝 커밋 |
| Global Constraints | 모든 태스크에 적용되는 설계 문서의 고정 요구사항 |
| Review Focus | 테스트가 놓치기 쉬운 입력·실패 상황 5가지 |
